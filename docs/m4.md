# M4 GitHub 交付契约

版本：M4-delivery-v1。GitHub 功能仅由可信配置启用；本地任务保留原有验收语义。`github` 配置冻结仓库名称与数字 ID、目标 base、发布许可、可信反馈者数字 ID/login/范围、非空 requiredChecks（名称及 GitHub App ID）、有限轮询间隔/次数/页数。未知配置被拒绝。

`task import --issue N --key KEY` 在已登记开发仓库中导入指定公开/私有 issue 的当前快照。保存 issue ID、更新时间、内容摘要和原文；同键重试保留原快照，来源和 Task 同事务创建。外部文本只能作为需求，不能配置命令、路径、模型、凭据、预算或交付权限。后续 issue 编辑不自动修改已导入需求。

控制层通过官方 GitHub REST（固定 api.github.com，版本 2026-03-10）访问；凭据由本机 gh 认证读取，不传递给 Agent。原始任务和凭据只保留在私有目录。

本地验收与远端交付独立：`accepted` 仍要求当前需求/提交的完整成果、可信验证、独立审查、未解决发现为空、干净工作树及全部执行占用释放。交付意图绑定来源摘要、需求版本、候选 SHA、base SHA、期望远端 SHA、专属分支及持久 PR marker。意图先于副作用提交；每个步骤只可领取一次，未知结果必须核对，不直接重放。

远端适配器只向固定 GitHub 仓库普通推送，不 force，不 merge。base、远端 head、PR 身份/marker/状态均需匹配。原生 push 使用持久守护进程；核对停止状态后才采信远端结果。PR POST 结果未知时查询包含关闭状态的完整 PR 列表，匹配已有结果；仍未知则阻塞，不重复 POST。分页超过可信页数上限显式失败。PR 自动随分支更新；应用不覆写用户的 PR 标题/正文。

轮询先事务消耗次数并记录下次时间，使用任务原绝对截止时间。每次读取完整有界评论集合，持久 ETag/body 支持条件请求；来源 ID、更新时间和正文摘要共同去重，因此旧评论编辑不会被时间 cursor 隐藏。自己的已登记事件 ID 被抑制；同一登录者的独立评论仍进入收件箱。任何分页不完整都不能提交新 CI/收件箱证据。限流遵循 Retry-After、reset 和 x-poll-interval，普通权限拒绝直接阻塞。

CI 只接受指定 head SHA 上可信 App 的非空冻结检查集合；同 suite 的新 rerun 替换旧结果，不同 suite 全部成功才通过。缺失、pending、未知、重名不可信上下文、传统 status 同名歧义均不通过。普通 failure 保守归为基础设施/未知；仅冻结 codeStep 对应的 GitHub Actions job 在当前 SHA 上、此前 setup 全成功且该项目检查步骤明确失败时，才路由代码修复。取消/超时不自动花费模型调用。

反馈格式为 `/relay {"kind":"requirement","requirementVersion":1,"revision":"<当前40位SHA>","files":["example.md"],"text":"明确的反馈"}`。kind 可为 requirement/implementation/design；身份数字 ID 与 login、角色范围、文件范围、版本和 SHA 都须匹配。普通评论不触发执行；额外字段拒绝。需求变更升级版本并重新 triage，修复/设计反馈保留需求版本并返回对应阶段；均消耗同一迭代预算，原运行次数、轮询次数和截止时间不重置。全部原有未解决发现门禁保留。

本地 succeeded 只表示本地候选已验收；GitHub watching 表示在有限窗口内等待 CI/反馈。有效反馈原子进入 waiting_local 并重新排队；complete 是显式关闭反馈窗口的远端终态，需要新鲜的当前 CI、当前本地验收和已处理收件箱。基础设施/权限失败阻塞，不自动当作代码问题花费模型调用。

首次发布使用 `task publish ID --version N`。服务自动核对持久意图、轮询并消费反馈，修复重新验收后更新同一 PR。`task reconcile-delivery ID --version N` 允许在外部条件恢复后核对 blocked 交付，保留原次数/截止时间，不重放未知副作用。`task complete-delivery ID --version N` 显式关闭反馈窗口；`task cancel-delivery ID --version N` 立即停止新远端操作，仍展示已发生的分支/PR。它不撤销已发布内容，也不取消独立的本地实现；后者使用原 task cancel。status 同时返回 accepted、delivered、deliveryIntent、deliveryCI 和收件箱处置记录。

故障核对保持原步骤领取记录：更新 PR 的 push 已在远端成功但本地回执丢失时，先证明旧进程停止，再区分旧 head、预期新 head 和外来 head。只有预期新 head 可补记成功。取消不会被晚到的核对/准备结果覆盖。轮询代次与当前意图共同阻止旧响应覆盖新 CI；尚未消费的评论旧版本标记 superseded，已应用决定不改写。PR base 必须等于本地验收工作树的基线，避免向旧 base 发布无关历史。

确定性验证包括响应丢失、更新回执丢失、提交收据前崩溃、关闭/合并/删除/外来修改、取消竞态、未知所有权、分页不全、编辑/自身/不可信评论、乱序轮询、预算及版本失效。真实验收与最终 CI 结果在完成后单列，不由模拟测试代替。

实现/设计类外部反馈与已确认的项目 CI 失败生成稳定 G-* 待解决项，绑定需求版本及来源事件键。applied 只表示已路由；实施者必须逐项回应，独立审查必须明确解决，旧验收覆盖和检查成功不能替代解决证据。已知完成的旧交付在本地修复恢复后，可经显式 reconcile 对新候选进入 waiting_local，原远端 SHA 仍作为下一次更新的预期值。

## 配置与使用

将 [GitHub 配置片段](../examples/m4.github.json) 合入私有 M2 config，并核对数字仓库 ID、actor ID、检查 App ID/名称和 codeStep；示例默认 publish:false。工作 checkout 的 HEAD 必须是冻结的 PR base 提交；设置有限且足够覆盖模型与 CI 的 maxTaskMs。配置仍只作用于新任务。首次 publish 是本机可信操作，不由 issue 或评论授权。

先启动原 serve --config --runtime 服务，task import 后等待本地 accepted；使用 task publish，查看 status 的 delivery/CI/inbox，最后 complete-delivery。所有交付命令带当前 task --version。PR 保持打开供人审查；终态不表示合并。仅支持 github.com、同仓库 head/base、issue 与 PR 顶层评论；不自动消费 review-thread 或 webhook。Linux 仍只声明确定性验证，原生 Codex 实测限 Windows。

REST 契约参考 [PR](https://docs.github.com/en/rest/pulls/pulls)、[评论](https://docs.github.com/en/rest/issues/comments)、[检查](https://docs.github.com/en/rest/checks/runs)、[Actions job](https://docs.github.com/en/rest/actions/workflow-jobs) 与 [限流/条件请求](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)。应用不跟随外部正文提供的 URL。
