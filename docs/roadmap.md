# Roadmap

## v1：Codex CLI 研发编排

按 [实现计划](implementation-plan.md) 完成 M0–M4。只开发一个真实执行后端，保留经过模拟执行器验证的扩展接口，不提前编写空的供应商实现。

## 后续 A：官方 API Agent 运行时

目标：在同一工作流中运行直接模型 API 驱动的 Agent。首批候选包括 DeepSeek 官方 API，其他供应商按需要增加。不会将 Codex 支持 DeepSeek 作为该路线前提。

### A1：只读分析与审查

- 在 Agent 执行接口下增加 API runtime。
- 使用供应商官方 API/SDK，适配流式响应、错误、用量与模型原生参数。
- 第一阶段基于明确提供的成果包输出审查；需要仓库调查时提供受限读取/搜索工具。
- 能力不足以完成审查时返回缺少证据，不假装全面检查。
- 外部会话格式不进入工作流核心；上下文以任务成果重建。
- 凭据仅从本地安全配置引用，不写入任务、公开配置或日志。

验收：同一工作流可选择 Codex 实现、API Agent 审查；模型切换无需修改状态机；错误与用量可归因。

### A2：自研 harness 的工具执行循环

- 定义工具 schema、调用 ID、工具结果配对与最大循环次数。
- 实现受限读写、补丁应用、命令执行及独立验证。
- 建立上下文预算、截断和压缩策略，保留任务约束与可追溯成果引用。
- 对工具执行结果未知进行核对，禁止盲目重复副作用。
- 使用实际沙箱/权限机制限制目录、网络和进程；提示词不是安全边界。
- 实现多轮续接、超时、取消、检查点、注入抵抗与日志脱敏。

验收：除功能链路外，覆盖越界写入拒绝、取消后无遗留进程、工具结果丢失、上下文溢出及故障恢复。API 能返回文本不足以宣布 harness 可用。

### A3：模型组合评测

比较单 Agent、同模型分工和异模型分工。在相同任务、验收与预算下衡量收益；记录模型与运行时版本。不同 harness 的结果只用于系统级比较，不能归因于模型本身。

## 后续 B：按政策自动合并

独立于 API Agent，可按实际需求先行。仅处理明确授权类别；检查当前 head SHA、必要 CI、审查与仓库保护规则。禁止通过降低门禁或绕过保护合并。基线变化触发必要复验；取消与合并竞态必须先核对结果。

## 后续 C：Web 界面与并发

基于现有本地服务展示任务、模型配置、证据、成本与待决事项，再扩展受控多任务并发。每任务工作区和写租约仍独立。

远程 worker、多用户、动态拓扑、插件市场与长期记忆仅在真实需求出现后评估，不列入近期承诺。

## 进入后续阶段的依据

优先修复试点中暴露的失效模式。对每项扩展说明：用户需求、现有能力缺口、维护成本、验证方法和退出条件。不会因“更多 Agent/模型”本身而增加复杂度。
